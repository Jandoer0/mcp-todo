## 1. Горизонтальная канбан-доска по образцу Planka (десктоп)

Сейчас списки — вертикальные «группы» (`Board.jsx`: секции сверху вниз, внутри `md:columns-2`, сворачивание секций), перенос карточек — свайпом. Требуется классическая горизонтальная канбан-компоновка; образец оформления и взаимодействия — **Planka** (https://github.com/plankanban/planka): колонки-списки в горизонтальный ряд, карточки стеком внутри колонки, перенос карточек перетаскиванием.

| № | Требование |
|---|---|
| 1.1 | Десктоп (ширина ≥ md): все списки доски — горизонтальный ряд колонок; контейнер скроллится по горизонтали, колонки занимают полную высоту рабочей области; карточки внутри колонки — вертикальный стек с собственным скроллом при переполнении. |
| 1.2 | Колонка: шапка с цветовым маркером списка, названием и счётчиком карточек; кнопка «+» для быстрого добавления задачи прямо в эту колонку; меню колонки (переименовать/цвет/удалить) — из существующего ListsManager, по месту. |
| 1.3 | Перенос карточек — **drag-and-drop между колонками** (HTML5 DnD или библиотека вроде dnd-kit): полупрозрачность перетаскиваемой карточки, подсветка колонки-приёмника, вставка в конкретную позицию стека. Перетаскивание внутри колонки меняет порядок задач. |
| 1.4 | Добавить задачам поле `position` (порядок внутри колонки; дробный индекс с зазором или LexoRank), миграция + бэкфилл существующих задач. REST: сортировка `list_tasks` по `(list, position)`, эндпоинт переупорядочивания (один запрос на перенос: `{task_id, list, position}`). |
| 1.5 | Серверная валидация при DnD не ослабевает: инвариант «циклическая ⇔ Регулярные» действует и при перетаскивании (сейчас — через `_enforce_regular_list`; сохранить поведение: циклическая не уезжает из «Регулярных», обычная туда не попадает). |
| 1.6 | Свайп-перенос на мобильных сохранить (там, где он разрешён: для не-циклических); на десктопе основным способом переноса является DnD. |
| 1.7 | Оформление карточек — по образцу Planka: скруглённая плашка на полупрозрачном фоне, заголовок до 2 строк, компактная нижняя строка метаданных (дедлайн, теги-чипы, сумма — см. §3, бейдж блокеров, приоритет-точка). Избегать визуального шума: чипы — только когда поле заполнено. |
| 1.8 | Done-списки («Готово», «Архив»): сворачиваемые колонки, свёрнутые по умолчанию (сейчас «Архив» свёрнут — поведение сохранить; распространять ли на остальные done-колонки — решить при проверке). |
| 1.9 | Предохранитель «Прочее» (задачи с чужим именем списка): либо убрать совсем (починка при загрузке/миграция), либо показывать последней колонкой; сворачиваемую секцию снизу не оставлять. |
| 1.10 | Горизонтальная компоновка — только десктоп; на мобильных остаётся текущая вертикальная подача списков (адаптив уже есть — сохранить). |

## 2. Циклические задачи: отдельное диалоговое окно создания/редактирования

Сейчас поля цикличности (галочка «Циклическая задача», период, интервал, напоминание) встроены в общую `TaskForm.jsx` и жёстко связаны с селектором статуса (автопереключение на «Регулярные», disabled). Это запутывает форму обычной задачи. Требуется переосмысление: **у циклических задач — собственное окно**, отделённое от формы обычной задачи.

| № | Требование |
|---|---|
| 2.1 | Отдельный компонент `CyclicTaskForm` (модалка в существующем стиле): название, описание, сумма + валюта (доход/расход), период (`daily/weekly/monthly/yearly`), интервал N, напоминание за N дней, теги. |
| 2.2 | Обычная форма задачи (`TaskForm`) больше не содержит блок цикличности: галочка, период, интервал, `reminder_days` из неё убираются; селектор статуса в обычной форме никогда не блокируется. |
| 2.3 | Точки входа: кнопка в колонке «Регулярные» («+ Добавить задачу» открывает циклическую форму); редактирование циклической — из её карточки, открывает `CyclicTaskForm`. Отдельная кнопка в шапке не нужна — стандартным способом создания остаётся системный список «Регулярные». |
| 2.4 | Конверсия в обе стороны: в `CyclicTaskForm` кнопка «Сделать обычной» (вызывает существующий `cycle/stop`); обычная задача через общую форму циклической стать не может (только создание в циклическом окне). |
| 2.5 | Карточка циклической задачи помечается заметным признаком (иконка цикла/бейдж с периодом, напр. «↻ ежемесячно») — тип задачи виден без открытия окна. |
| 2.6 | В окне циклической задачи — компактная сводка истории итераций: последние N выполнений (дата план/факт, сумма план/факт) + кнопка «Вся история» (существующий диалог истории) и корректировка факта задним числом (существующий PATCH `/cycle/history/{log_id}`). |
| 2.7 | Список «Регулярные» в десктопной компоновке (§1) — колонка с тем же защитным поведением; обычную задачу перетащить в неё нельзя (подсветка ошибки, отмена переноса с пояснением). |
| 2.8 | MCP: изменений поведения не требуется — `create_task`/`update_task` продолжают работать с циклическими полями как сейчас (серверный слой общий). |

## 3. Сумма на карточке вместо значка $

Сейчас при `amount != 0` карточка показывает безликий бейдж `+$` / `-$` (`TaskCard.jsx`, бейдж справа в заголовочной строке). Требование: **на карточке отображается сама сумма**.

| № | Требование |
|---|---|
| 3.1 | Бейдж суммы: знак, отформатированное число (`toLocaleString('ru-RU')`, helper `formatAmount` уже есть) и **символ валюты задачи** (`task.currency_id` → символ из `currenciesApi`; валюта не задана — валюта по умолчанию пользователя). Пример: `+10 000 ₽`, `−1 200 $`. |
| 3.2 | Цветовая логика сохраняется: доход/расход различимы (сверить с текущим `text-amber-400` и палитрой приложения; главное — не терять знак и семантику доход/расход). |
| 3.3 | Крупные суммы сокращать на карточке: `12 500 000` → `12,5 млн`, `4 200` → `4,2 тыс.`; полное значение — в `title`/подсказке и в окне задачи. |
| 3.4 | У циклических задач на карточке — плановая сумма (текущий `task.amount`); факт живёт в истории итераций (окно §2.6), дублировать факт на карточке не нужно. |

## 4. Объединение вкладок «Бюджет» и «График» → одна вкладка «Бюджет» (`BoardForm.jsx`)

Сейчас две вкладки: `BudgetTab` (итоги и записи) и `ChartTab` (график денежного потока). Требование: одна вкладка «Бюджет» с **переключателем отображения баланса доски**: итоги ↔ график.

| № | Требование |
|---|---|
| 4.1 | Одна вкладка «Бюджет» (убрать «График» из набора табов `BoardForm.jsx`); внутри — сегмент-переключатель в стиле приложения (напр. `[Итоги | График]`); выбор запоминается (localStorage или состояние доски). |
| 4.2 | Режим «Итоги» — текущее содержимое `BudgetTab`: ПЛАН/ФАКТ/ИТОГО, базовый слой (регулярные) vs разовые, записи с метками. |
| 4.3 | Режим «График» — текущее содержимое `ChartTab` (SVG-график, факты/прогноз, кассовые разрывы, детализация дня, навигация стрелками/плавающими кнопками). Существующие компоненты переиспользовать почти без изменений — меняется оболочка, не содержимое. |
| 4.4 | Валюта расчёта доски (`report_currency`) выбирается один раз на вкладке и действует в обоих режимах. |
| 4.5 | Данные: сейчас компоненты запрашивают бюджет/график независимо — допустимо оставить, но предпочтительно вынести общий загрузчик (budget + cashflow) на уровень вкладки, чтобы переключение режимов было мгновенным и без дублирующих запросов. |
| 4.6 | Мобильная версия: переключатель доступен, график сохраняет плавающие кнопки навигации по дням и клавиатурную навигацию на десктопе. |

## Критерии приёмки

1. На десктопе списки — горизонтальные колонки; DnD-перенос карточек между колонками и внутри колонки работает, порядок сохраняется после перезагрузки (поле `position` на сервере); свайп на мобильных работает как прежде.
2. Циклическая задача создаётся и редактируется только в своём окне; обычная форма задачи не содержит циклических полей; «Регулярные» защищены от попадания обычных задач при DnD (сервер + UI).
3. Карточки с ненулевой суммой показывают сумму с символом валюты (например `−1 200 ₽`), а не `+$`/`-$`.
4. Вкладка одна — «Бюджет», с переключателем «Итоги/График»; всё прежнее содержимое обеих вкладок доступно.
5. Фильтры по статусу/тегам, цветовая гамма и стиль модалок не изменились.
6. Тесты: добавить бэкенд-тесты на `position` (создание, перенос, порядок, инвариант «циклическая ⇔ Регулярные» при переносе); для фронтенда — ручной чек-лист по §1–4 (или первые smoke-тесты).
7. README обновить: раздел «Возможности» (горизонтальная доска, отдельная форма циклических, бейдж суммы с валютой, объединённый бюджет) и таблицу REST-эндпоинтов (переупорядочивание задач).

| № | Предложение | Обоснование |
|---|---|---|
| 5.1 | CI: прогонять `pytest` перед сборкой образа в `build.yml` | Сейчас мастер может уйти вперёд с регрессией; тесты быстрые (~15 с) |
| 5.2 | Денежные суммы хранить целыми копейками/минорными единицами (`Integer`) или Decimal-строкой вместо `Float` | Конвертация уже Decimal, но сама колонка float — риск накопления ошибок при правках факта задним числом |
| 5.3 | Почистить каскады: `task_tags`/`task_change_logs` при удалении цепочки цикла и доски (`synchronize_session=False` не трогает junction) | Осиротевшие строки копятся и попадают в квоту БД |

| 5.6 | Фронтенд: вынести `formatAmount`/форматирование валют в общий модуль, добавить smoke-тесты на форму задачи и бейдж суммы | Компоненты 600–800 строк правятся вслепую; регрессии §2–3 проще ловить тестами |
| 5.7 | Проверить актуальность демо-аккаунта после переработки доски | Демо должен показывать новую горизонтальную доску и суммы на карточках с первого экрана |
